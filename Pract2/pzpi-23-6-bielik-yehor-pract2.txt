2 ЗАВДАННЯ
     Метою цієї роботи є вивчення архітектури складної програмної системи, а також аналіз використаних у ній архітектурних рішень. У процесі виконання завдання передбачається дослідити побудову обраної системи, визначити її архітектурний стиль, охарактеризувати ключові компоненти та їхню роль. Окрім цього, необхідно розглянути взаємодію між підсистемами, а також оцінити рівень масштабованості системи і переваги застосованих підходів до її проєктування.


3 ОПИС ВИКОНАНОЇ РОБОТИ
     3.1 Загальні відомості про систему 
     Об'єктом дослідження є платформа X - сервіс мікроблогінгу та соціальних комунікацій, що функціонує під управлінням компанії X Corp. Платформа веде свою історію з 2006 року під назвою Twitter; у жовтні 2022 року її придбав підприємець Ілон Маск за 44 мільярди доларів, після чого відбувся ребрендинг. Основне призначення сервісу - надання користувачам інструментів для публікації коротких текстових і мультимедійних повідомлень, перегляду персоналізованої стрічки новин, пошуку контенту в реальному часі та приватного листування. Сервіс доступний через браузер, застосунки для iOS і Android, а також через відкритий програмний інтерфейс для зовнішніх розробників. За актуальними даними на 2024 рік, щодобова аудиторія перевищує 250 мільйонів осіб, а кількість публікацій сягає близько 500 мільйонів на день. Такі показники навантаження зумовлюють потребу в особливо ретельно спроєктованій програмній архітектурі, яка і є предметом цієї роботи.
     3.2 Архітектурний стиль системи 
     Технічну основу X формує поєднання мікросервісного та подієво-орієнтованого підходів. Функціональність платформи розподілена між незалежними сервісами, кожен з яких відповідає за окремий домен: формування стрічки, публікацію записів, повнотекстовий пошук, сповіщення, роботу з медіафайлами, автентифікацію та обмін повідомленнями. Усі міжсервісні взаємодії побудовані на асинхронному обміні подіями через Apache Kafka, завдяки чому сервіси не залежать один від одного безпосередньо. Зовнішні запити потрапляють до системи через єдиний API Gateway, який бере на себе маршрутизацію, перевірку прав доступу та обмеження частоти звернень.Такий підхід продиктований масштабом задачі: незалежне розгортання сервісів спрощує внесення змін без ризику для всієї системи, а асинхронна модель дозволяє витримувати різкі сплески активності без деградації продуктивності.
     3.3 Основні компоненти системи 
     Архітектура X охоплює кілька структурних рівнів. На клієнтському рівні працюють веб-інтерфейс на React/Next.js та нативні мобільні застосунки - Swift для iOS і Kotlin для Android. Зв'язок із серверною частиною здійснюється через REST та GraphQL.
     Перед основними сервісами розташований проміжний рівень із CDN-сервісом Fastly, що прискорює доставку статичного контенту, та балансувальниками на базі HAProxy і Nginx.
     Серцем системи є сервісний рівень: API Gateway приймає всі вхідні запити; Tweet Service відповідає за збереження та видалення публікацій; Timeline Service формує стрічку новин і реалізує механізм Fan-out; Search Service забезпечує пошук у реальному часі на базі Apache Lucene та власного рушія Earlybird; Notification Service розсилає сповіщення; Media Service опрацьовує графічні та відеоматеріали; Auth Service керує автентифікацією за стандартами OAuth 2.0 та JWT.
     Рівень збереження даних вирізняється різноманітністю технологій. Твіти зберігаються у власній NoSQL-базі Manhattan, побудованій поверх RocksDB. Реляційні дані користувачів розміщені в MySQL із горизонтальним шардингом через Gizzard. Redis використовується для оперативного кешування стрічок і сесій. Apache Kafka виконує роль брокера подій між сервісами. Hadoop і Hive обслуговують аналітичні задачі. Медіафайли зберігаються у Blobstore, а пошуковий індекс реального часу ведеться в Earlybird.
     3.4 Взаємодія компонентів 
     Клієнти звертаються до платформи через HTTPS, всі внутрішні міжсервісні взаємодії відбуваються асинхронно через Kafka.
     Розглянемо сценарій публікації твіту. Після того як користувач надсилає запит на /2/tweets, API Gateway перевіряє токен і передає його до Tweet Service. Сервіс записує публікацію до Manhattan і розміщує подію в топік Kafka. Далі Fan-out Service зчитує подію і наповнює Redis-кеш підписників. Паралельно Notification Service формує сповіщення, а Search Indexer оновлює пошуковий індекс - обидва незалежно підписані на той самий топік.
     Особливої уваги заслуговує логіка Fan-out. Для більшості акаунтів твіт записується одразу в кеш кожного підписника в момент публікації - це підхід Fan-out on Write. Однак для акаунтів із десятками мільйонів підписників такий підхід спричинив би надмірне навантаження, тому для них застосовується Fan-out on Read: твіт підтягується з бази в момент, коли підписник відкриває стрічку.
     3.5 Масштабованість та надійність 
     Розподіл вхідного трафіку забезпечується на двох рівнях - зовнішньому через HAProxy/Nginx та внутрішньому через API Gateway. Між сервісами реалізований патерн Circuit Breaker, що локалізує збої та не дає їм поширюватися на інші частини системи. Кешування в Redis суттєво розвантажує основні бази даних при читанні стрічок. Уся інфраструктура оркестрована в Kubernetes з підтримкою автомасштабування, розгорнутому на потужностях AWS та GCP. Стан системи відстежується через Prometheus і Grafana.
     Окремо варто відзначити трансформацію інфраструктури після зміни власника у 2022 році. Кількість задіяних серверів скоротилася приблизно вдвічі, частину власних дата-центрів було виведено з експлуатації, а витрати на хмарні ресурси значно знизились. Те, що платформа зберегла стабільну роботу за таких умов, свідчить про достатній запас міцності мікросервісної архітектури та ефективність прийнятих інженерних рішень.
     3.6 Приклади програмної реалізації 
     Для ілюстрації архітектурних принципів розглянуто два сценарії роботи з X API v2. Перший - створення публікації. Клієнт виконує POST-запит до /2/tweets, передаючи в заголовку Bearer-токен і в тілі запиту JSON із текстом повідомлення. Платформа повертає об'єкт із присвоєним ідентифікатором твіту. Другий сценарій - читання хронологічної стрічки. GET-запит до /2/users/:id/timelines/reverse_chronological з параметрами обмеження вибірки та переліком потрібних полів повертає масив публікацій разом із токеном для переходу до наступної сторінки результатів. Обидва приклади наочно демонструють stateless-природу взаємодії, стандарти RESTful-проєктування та модель токенової автентифікації. Програмний код наведено у Додатку В. 
	Презентація налічує одинадцять слайдів і охоплює всі ключові аспекти дослідження: від загального огляду платформи до детального розбору механізму Fan-out та прикладів роботи з API. Слайди містяться у Додатку Б, відеозапис - у Додатку А. 
     
     


4 ВИСНОВКИ
     У результаті виконання практичного заняття досліджено архітектуру платформи X. Встановлено, що система побудована на поєднанні мікросервісного та подієво-орієнтованого стилів із використанням Apache Kafka як брокера подій, що забезпечує повну асинхронність міжсервісної взаємодії та ізоляцію збоїв. Ключовим інженерним рішенням є гібридний механізм Fan-out, а принцип Polyglot Persistence підтверджує доцільність використання спеціалізованих сховищ для різних типів даних. Досвід скорочення інфраструктури після 2022 року засвідчив, що грамотно спроєктована архітектура здатна зберігати працездатність навіть за умов суттєвого зменшення ресурсів.
     За підсумками роботи сформовано практичні навички архітектурного аналізу програмних систем, вивчено підходи до масштабування розподілених платформ реального часу та отримано досвід роботи з публічним API на прикладі X API v2.
